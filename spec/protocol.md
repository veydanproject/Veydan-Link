# VLink: протокол

Версия 1. Три участника: клиент, мост (`vlink`), хаб (`vhub`). Четвёртый — реестр, часть одного из хабов.

## Идентичность

- **Мост (идентичность v2).** Два ключа. *Ключ моста* — постоянный Ed25519 (`bridge.key`), делается при первом запуске; ID моста = SHA-256 от DER SubjectPublicKeyInfo этого ключа, 64 hex-символа. Им мост подписывает TLS-сертификат и отчёты реестру, больше ничем не пользуется. *TLS-ключ* — ECDSA P-256 (`tls.key`), на нём идёт рукопожатие: такой ключ принимает любой браузер, поэтому посторонний доходит до страницы 404 (раздел «Порт моста»), а не получает алерт, по которому мост отличим (Ed25519 в `signature_algorithms` браузеры не предлагают). Мост показывает цепочку из двух сертификатов (`bridge.crt`): сертификат над TLS-ключом, подписанный ключом моста, и за ним самоподписанный сертификат, несущий ключ моста. Клиент и хаб пинят ключ моста (как HPKP), а не сертификат: берут второй сертификат, сверяют хеш его ключа с ID, проверяют им подпись и срок первого и дают TLS 1.3 доказать TLS-ключ (схема `ecdsa_secp256r1_sha256`). Имена, даты выпуска и серийные номера не значат ничего. TLS-ключ и сертификат можно менять (`vlink id --renew-cert` делает новые, затем перезапуск моста): ID не меняется. Потеря ключа моста — новый мост. Мост при запуске проверяет свою цепочку тем же правилом; цепочку, подписанную не его ключом, не принимает и останавливается с подсказкой `--renew-cert`; ключ другого типа в `bridge.key` (P-256 моста до v2) — с подсказкой удалить три файла. Совместимости со схемой v1 (хеш сертификата) нет.
- **Ссылка на мост:** `адрес:порт#id`, необязательно `?sni=имя`. Пример: `203.0.113.7:443#5ebb…95de`. Для приложения та же ссылка пишется как `veydan://vlink/<id>?a=<адрес:порт>` (`vlink link --addr …`); слово `bridge` в ссылках приложения оставлено для мостов в другие сети, `veydan://bridge/…` приложение не принимает.
- **Корень VLink.** Один ключ Ed25519, хранится вне серверов. Его сертификат и открытый ключ зашиты в `vlink` (`trust/root.crt`, `trust/root.pub`).
- **Хаб.** Сертификат X.509 с EKU clientAuth, подписан корнем, срок 90 дней. Мост принимает любой хаб с таким сертификатом, откуда бы тот ни звонил.
- **Клиент** ничего не предъявляет.

## Порт моста

Один порт, TLS 1.3. Кто пришёл, мост определяет после рукопожатия:

| ALPN | Сертификат клиента | Кто это | Что дальше |
|---|---|---|---|
| `vlink-hub/1` | подписан корнем | хаб | соединение становится связью |
| `h2` | нет | клиент | потоки `CONNECT` |
| `http/1.1` или нет | — | посторонний | страница 404 «nginx» |

Запрос h2 с методом, отличным от `CONNECT`, получает ту же страницу 404.

SNI: клиент и хаб звонят на IP, поэтому по умолчанию SNI не отправляется. Поле `sni` в ссылке задаёт имя, если оно понадобится.

## Связь хаб → мост

Дозванивается хаб. Поверх TLS — HTTP/2 с перевёрнутыми ролями: TLS-клиент — хаб, h2-клиент — мост. Потоки открывает мост.

Настройки h2 на обоих участках: окно потока 4 МиБ, окно соединения 32 МиБ. PING раз в 20 с, ответ ждут 15 с; без ответа соединение считается мёртвым. Замёрзшее соединение иначе не обнаружить: оно не закрывается.

**Проверка связи.** Новую связь мост сначала испытывает: открывает поток к `probe.vlink:1` и гонит 512 КБ в каждую сторону, срок 20 с. Только после этого на связь попадают клиенты. Хаб, от которого байты не доходят, отклоняется.

## Поток

Клиент → мост и мост → хаб — один и тот же запрос:

```
:method = CONNECT
:authority = <имя хоста>:<порт>
vlink-peer: <ip:порт клиента>      только на участке мост → хаб
```

Хост — DNS-имя в нижнем регистре. IP-адрес в `:authority` не принимается.

Ответы:

| Статус | Значение | Что делает клиент |
|---|---|---|
| 200 | поток открыт, дальше байты в обе стороны | — |
| 403 | хоста нет в манифесте или порт не 443 | не повторяет |
| 502 | хаб не дозвонился до сервера | не повторяет |
| 503 | у моста нет ни одной связи | берёт другой мост |
| 400 | неразборчивая цель | — |

Внутри потока клиент ведёт собственный TLS к серверу и проверяет его настоящий сертификат. Мост и хаб содержимого не видят.

**К серверу** хаб подключается по TCP на порт `[upstream] port`. При `proxy_protocol = true` первым идёт заголовок PROXY v2 с адресом клиента из `vlink-peer`. Мост может солгать в этом заголовке.

## Служебные цели

Хосты `*.vlink` хаб обслуживает сам, порт всегда 1.

`probe.vlink:1` — отдаёт и принимает байты:

```
GET <n>\n            → n байт
PUT <n>\n n байт     → OK <n>\n
```

Команд на одном потоке может быть несколько. Предел — 1 ГиБ на команду.

## Реестр

HTTP, JSON. Стоит за nginx на хосте из манифеста, поэтому доступен и напрямую, и через любой мост.

```
POST /vlink/v1/register        мост сообщает о себе         без токена
GET  /vlink/v1/list            список мостов для клиента    без токена
GET  /vlink/v1/hub/bridges     кого обзванивать             токен хабов
GET  /vlink/v1/probe/targets   кого проверять               токен зондов
POST /vlink/v1/probe/report    результат проверки           токен зондов
GET  /vlink/v1/canary?bytes=N   N байт (до 512 КБ)           без токена
POST /vlink/v1/canary           принимает тело до 512 КБ, 204 без токена
```

Канарейкой приложение проверяет свой прямой путь к серверам: проходят ли по нему сотни килобайт.

Токен — `Authorization: Bearer …`.

**Регистрация.** Тело: `{"id","port","ip"?,"hubs","version","ts","key","sig"}`. Адрес моста — `ip` из тела, а если его нет, адрес, с которого пришёл запрос. Ответ: `{"state","addr"}`. Мост повторяет запрос раз в 30 с, пока он `new`, и раз в 5 минут после.

Регистрация подписана ключом моста: `key` — его открытый ключ, 32 байта hex (ID — его хеш), `ts` — unix-секунды отправки, `sig` — подпись Ed25519 под `"vlink-register/1\n" + id + "\n" + ip-или-пусто + "\n" + port + "\n" + hubs + "\n" + version + "\n" + ts + "\n" + key`. Реестр принимает запись, только если хеш `key` равен `id`, подпись верна и `|ts − сейчас| ≤ clock_skew_secs` (300). Так никто другой не может сообщить ID моста со своего адреса и выбить мост из списков, а старую регистрацию нельзя послать повторно.

**Состояния моста:**

| Состояние | Как попасть | Хабы звонят | Клиентам выдаётся |
|---|---|---|---|
| `new` | первая регистрация или смена адреса | нет | нет |
| `verified` | хаб реестра дозвонился, и мост доказал ключ с этим ID | да | нет |
| `active` | зонд прогнал байты, испытательный срок прошёл | да | да |
| `degraded` | один неудачный зонд | да | нет |
| `dead` | три неудачных зонда подряд или 15 минут молчания | да | нет |
| `banned` | команда администратора | нет | нет |

Удачный зонд возвращает `degraded` и `dead` в `active`. Мост, молчащий 7 дней, забывается.

**Отказы регистрации (403):** нет подписи или подписано не ключом этого ID; часы моста расходятся с реестром больше чем на 5 минут; адрес не публичный; адрес вне разрешённых диапазонов; в его /24 (для v6 — /48) уже `per_subnet` мостов; мостов уже `max_bridges`; мост забанен.

## Подписанный список

```json
{
  "list": "{\"v\":1,\"issued_at\":…,\"expires_at\":…,\"bridges\":[\"адрес:порт#id\",…]}",
  "sig": "<hex>",
  "delegation": {"key": "<hex>", "expires_at": …, "sig": "<hex>"}
}
```

- `delegation.sig` — подпись корня под `"vlink-list-key/1\n" + key + "\n" + expires_at`.
- `sig` — подпись ключа списков под `"vlink-list/1\n" + list`. Подписан текст поля `list` как есть.
- Клиент проверяет обе подписи и оба срока. Срок списка — 7 дней.

**Кому какие мосты.** Клиент получает не больше `list_size` (8) активных мостов. Выбор: для каждого моста считается HMAC-SHA256(секрет, сутки ‖ /24 клиента ‖ ID моста), берутся наименьшие. Один район в одни сутки получает одни и те же мосты; целиком список не получает никто.
